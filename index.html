The Restaurant Analogy

Food for Thought

Let's break down the core components of AI agents—LLMs, RAG, MCP, APIs, Semantics, and Data—what each does, why it matters, and when you can (and can't) do without it.

🧠

LLM (The Brain)

You deciding what to eat. Without a brain, ingredients, recipes, and waiters all exist — but no one chooses, combines, or adapts.
In AI terms: The reasoning engine. It interprets intent, generates SQL, picks tools, and synthesizes answers.

Skip it when: Everything is pre-decided (set menu, fixed reports, canned queries). No flexibility needed.

Without it: Just a static system. Nothing adapts. Not an "agent."
Cost of missing: No intelligence = no agent. System is static.
📚

RAG (Memory / Reviews)

Checking reviews or past orders. "Last time I had the fish and it was great." Without memory, you're ordering blind every time.
In AI terms: Retrieval-augmented generation. Pulls relevant docs, past queries, and domain context into the prompt.

Skip it when: Questions are simple and self-contained. "What's 2+2?" doesn't need context.

Without it: More hallucination. Generic answers. Misses "I'm allergic to peanuts" context.
Token cost: LLM compensates by reasoning harder — more tokens spent guessing context that could've been retrieved.
📋

MCP (The Menu)

The menu listing what you can order. Without it, the kitchen and waiter exist — but you don't know what's available. "Can you make pasta? Do you even have dessert?"
In AI terms: Model Context Protocol. Standardized tool discovery — the AI knows what capabilities exist.

Skip it when: Few tools, obvious options. A burger stand doesn't need a 20-page menu.

Without it: Custom wiring for every tool. Model can't discover capabilities. Must hard-code integrations.
Token cost: Agent wastes tokens probing for available tools — "can you do X?" loops before acting.
🤵

API / Tools (The Waiter)

The waiter who takes your order to the kitchen. You decide "I want a burger" — but without a waiter, nothing reaches the cook.
In AI terms: The execution layer. SQL runner, API calls, function invocations. Turns decisions into actions.

Skip it when: Self-service only. Buffet, kiosk, cooking at home — you act directly.

Without it: The model can plan but cannot act. Pure reasoning with zero execution.
Cost of missing: Nothing happens. Plans without execution = zero value.
📐

Semantic + Ontology (Recipes)

The recipe book. You see chicken, tomato, cream, spices — but without a recipe, there's no definition of "butter chicken." You guess. You get it wrong.
In AI terms: Semantic layer defines metrics ("revenue = SUM(amount) WHERE status='paid'"). Ontology encodes relationships ("Person works for Organization").

Skip it when: Simple queries. "SELECT * FROM users" doesn't need a recipe.

Without it: "Revenue" interpreted differently every time. Joins become guesswork. Exploratory questions explode in cost.
Token cost: 7× more reasoning tokens. Every query re-discovers what metrics mean and how tables connect.
🥩

Relational Tables / Data (Ingredients)

The ingredients in the kitchen. Recipes, menu, and waiter all exist — but the kitchen is empty. No food to cook.
In AI terms: Snowflake tables, Postgres, data warehouse. The actual rows and columns. Everything else is metadata about this.

Skip it when: Never. You always need data.

Without it: Perfect schema, zero data = useless. Nothing to query, nothing to return.
Cost of missing: Fatal. No data = no answers. Period.

Data engineers and analysts can use the CLI or Desktop to build agents, define workflows, create pipelines (dbt, Openflow, dynamic tables), and operationalize AI directly where the data lives.

Cortex provides the core building blocks — agents, search, analyst, and functions — that turn raw data into composable, production-ready intelligence.

The contrast: Many AI coding agents today connect directly to Snowflake tables and rely purely on LLM reasoning without using Cortex. While this works, it leads to overthinking, excessive token usage, higher cost, and more hallucinations — because the model has to infer context, logic, and relationships on its own. Snowflake changes this by grounding AI in governed data and shared logic. By enabling semantic layers (consistent metrics) and evolving toward ontologies (relationships and context), Snowflake reduces unnecessary reasoning and improves accuracy. The result is better unit economics across the entire stack — less time and compute spent "thinking," more value from knowing, acting, and scaling efficiently.

The Path to Efficient AI

Same Data, Different Context

Three stages of data maturity — each layer reduces AI overthinking. Same soccer data throughout.

1
Stage 1: Raw Relational Tables
Standard normalized schema. What most teams start with.
CLUBS (PK: CLUB_ID) ├── CLUB_NAME, COUNTRY, LEAGUE, FOUNDED_YEAR, STADIUM PERSONS (PK: PERSON_ID) ├── NAME, NATIONALITY, DATE_OF_BIRTH, ROLE, POSITION MATCHES (PK: MATCH_ID) ├── MATCH_NAME, EVENT_DATE, VENUE, HOME_TEAM_ID→CLUBS ├── AWAY_TEAM_ID→CLUBS, SCORE_HOME, SCORE_AWAY PLAYER_CONTRACTS (PK: CONTRACT_ID) ├── PERSON_ID→PERSONS, CLUB_ID→CLUBS ├── START_DATE, END_DATE, CONTRACT_VALUE, JERSEY_NUMBER COACH_CONTRACTS (PK: CONTRACT_ID) ├── PERSON_ID→PERSONS, CLUB_ID→CLUBS ├── START_DATE, END_DATE, CONTRACT_VALUE MATCH_APPEARANCES (PK: APPEARANCE_ID) ├── PERSON_ID→PERSONS, MATCH_ID→MATCHES ├── MINUTES_PLAYED, GOALS_SCORED, ASSISTS, CARDS

6 tables, clear column names, foreign keys. This is where every team begins — the data is correct, but there's no AI-ready layer on top.

2
AI Coding Agent vs. Raw Tables
The agent sees column names and FKs — but must reason about every relationship from scratch.
✓ "Who plays for Real Madrid?" → JOIN PERSONS + PLAYER_CONTRACTS + CLUBS (doable, 2 joins)
✓ "Goals scored by Messi?" → JOIN PERSONS + MATCH_APPEARANCES (doable, 1 join)
⚠️ "Which players worked with the same coach across clubs?" → Agent must discover the traversal path alone
No layer prevents overthinking. Simple questions work but cost unnecessary tokens (schema introspection every time). Exploratory questions cost 487K tokens, ~$1.52, ~600s — the agent rediscovers relationships from scratch.
3
Stage 2: Add a Semantic Model
AI + business experts define what the data means — creating a YAML semantic model over the tables.
── Same 6 tables as before ── CLUBS, PERSONS, MATCHES, PLAYER_CONTRACTS, COACH_CONTRACTS, MATCH_APPEARANCES ── NEW: Semantic Model (YAML for Cortex Analyst) ── soccer_semantic_model.yml defines: • "player" → PERSONS WHERE ROLE='PLAYER' • "coach" → PERSONS WHERE ROLE='COACH' • "plays_for" → PLAYER_CONTRACTS joined to CLUBS • "coaches_at" → COACH_CONTRACTS joined to CLUBS • "goals_scored" → SUM(MATCH_APPEARANCES.GOALS_SCORED) • "match_result" → MATCHES with HOME/AWAY scores

The semantic model defines what business terms mean — mapping natural language concepts to specific tables, joins, and aggregations. AI no longer guesses which table holds "goals" or what "plays for" means.

Cortex Analyst reads this YAML and resolves user intent in a single call for metric-based questions.
4
Semantic Model: Metric questions solved
Hard metric lookups are now trivial — the semantic model eliminates ambiguity.
✓ "Who plays for Real Madrid?" → Semantic knows: PLAYER_CONTRACTS + CLUBS, ~$0.05
✓ "How many goals did Messi score?" → Semantic knows: SUM(GOALS_SCORED), ~$0.05
✓ "Which coaches managed Barcelona?" → Semantic knows: COACH_CONTRACTS + CLUBS, ~$0.05
✓ "Top scorers by nationality" → Semantic knows: GROUP BY NATIONALITY, ~$0.08

For concrete, metric-based questions, semantics is transformative. Zero ambiguity = zero overthinking = fast answers at ~$0.05 each.

But what about: "Which players have indirectly worked with the same coach across different clubs?" — The semantic model defines entities, but doesn't encode cross-entity relationships. The agent still needs 6 tool calls, 272K tokens, $0.72.
5
Stage 3: Add Ontology on top
AI + business experts encode real-world relationships as first-class objects.
── Physical (KG_NODE + KG_EDGE) ── Same data, restructured as nodes and edges ── Semantic Views (same as Stage 2) ── V_PLAYER, V_COACH, V_CLUB, V_MATCH V_PLAYS_FOR, V_COACHES, V_PLAYED_IN ── NEW: Ontology Metadata ── ONT_CLASS: Person (abstract) → Player, Coach Organization → Club ONT_RELATION_DEF: "WORKS_FOR" (Person → Organization) "PARTICIPATES_IN" (Person → Event) ── NEW: Ontology Views (pre-encoded relationships) ── VW_ONT_PERSON: Unifies Players + Coaches as "Person" VW_ONT_WORKS_FOR: "Person works for Organization" (spans PLAYER_CONTRACTS + COACH_CONTRACTS) REL_RESOLVED: All relationships with class context

The ontology adds a knowledge layer that encodes real-world concepts: "A Player is a Person. A Coach is a Person. Both work for Organizations." These become queryable views — no discovery needed.

6
